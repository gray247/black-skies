# Writing Surface Sovereignty Rules

Status: Draft
Date: 2026-05-22
Phase: 30 - GUI / Workflow Realignment Spec
Pass: 1A - Workflow Philosophy Codification

## Purpose

This document defines the operational rules that protect Writing Surface sovereignty.
It does not define final placement or implementation mechanics.

## What Can Permanently Exist Near The Writing Surface

- direct authoring context
- minimal scene or unit context needed to avoid ambiguity
- bounded generation entry
- bounded save-state or project-state truth where necessary for trust
- compact status signals that directly affect current authoring safety or continuity

Permanent proximity must be justified by direct authoring relevance, not general usefulness.

## What Must Remain Contextual

- advisory interpretation
- pacing or structural observations
- model or routing detail beyond essential trust signaling
- temporary navigation aids
- support and recovery surfaces when no active exception exists

## What Must Remain Hidden Until Summoned

- advanced orchestration controls
- dense structural analysis
- command-style power access
- diagnostics and dev/test seams
- low-frequency support and verification tooling

## What Belongs In Rails

Rails may host:

- structural navigation
- contextual story state
- bounded support context
- temporary interpretive instruments

Rails should not become permanent dense telemetry stacks or duplicated control bars.

## What Belongs On Secondary Displays

When second-screen behavior is explored, the natural candidates are:

- structural navigation
- contextual intelligence that is not needed for immediate drafting
- support or recovery context during exception states
- advanced analysis and interpretive instruments

Second-screen candidacy does not equal permanent entitlement.

## What Counts As Redundant Metadata

Redundant metadata includes:

- repeated identity labels already obvious from the current working context
- multiple parallel state indicators for the same truth
- repeated structural labels that do not change user action
- telemetry that confirms what the surrounding UI already establishes

## What Counts As Duplicated Authority

Duplicated authority exists when:

- the same action is promoted in more than one primary surface without a distinct reason
- multiple surfaces claim to interpret the same narrative state simultaneously
- support and authoring controls coexist as peers when one should be subordinate
- the same trust signal appears in multiple visible authority tiers

## Acceptable Telemetry vs Noisy Telemetry

Acceptable telemetry:

- communicates current trust boundaries
- clarifies whether a workflow is safe, offline, escalated, or pending
- remains compact and task-relevant

Noisy telemetry:

- remains visible without changing user choice
- behaves like ambient system chatter
- competes with prose attention
- implies a narrative grade, rank, or score

## Bottom Action Bar Philosophy

If a bottom action bar exists in later exploration, it should serve as a bounded action seam rather than a status wall.

Rules:

- action authority must remain explicit
- it should not duplicate header, rail, and contextual controls
- it should not host dense analytics or narrative grading systems
- it should privilege deliberate action over passive telemetry

## Drag / Drop Interaction Expectations

Drag/drop is a first-class workflow primitive for structural manipulation when it helps writers reorganize narrative material directly.

Rules:

- drag/drop should primarily serve organization and placement
- drag/drop should not hide consequential mutation behind ambiguous gestures
- drag/drop should not silently merge authority classes
- drag/drop must preserve writing continuity rather than forcing mode breaks
