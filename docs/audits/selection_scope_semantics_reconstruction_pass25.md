## Selection Scope Semantics Model

This model is provisional only. It is not implementation authorization, not workflow-state canon, and not final product language.

Selection means a user or system has identified material, location, evidence, or context for possible later use. Selection is not permission. Scope is not execution. Scope may affect blast radius.

Provisional selection meanings:
- `Context`: selected material informs reading, drafting, advisory, or generation without being changed.
- `Target`: selected material is the focus of inspection, review, generation, or rewrite consideration.
- `Mutation Scope`: selected material defines what may be changed only after Mutation-Boundary Authority is entered.
- `Destination`: selected location or range receives generated, rewritten, restored, or inserted material.
- `Evidence`: selected material supports verification or support truth without authorizing repair.
- `Structural Hint`: selected material implies possible organization, grouping, or Story Unit pressure without authorizing persistence.

Semantic rules:
- selection is not permission
- selected target is not approved blast radius
- advisory context is not mutation authority
- verification evidence is not repair permission
- selected destination is not execution
- future command/search must inherit selection semantics rather than flatten them into command targets

## Executive Findings

- Selection scope is the most subtle Mutation-Boundary input because it often feels lightweight while defining target, destination, or blast radius.
- Selection must be reconstructed as multiple semantic families, not one generic highlighted state.
- Generation and Rewrite / Apply share one overarching mutation-boundary model, but selected scope affects each execution family differently.
- Advisory / Review may use selection as context, but it cannot convert that selection into rewrite/apply permission.
- Verification may select evidence or a problem area, but evidence selection must not become repair authority.
- Future command/search remains blocked until selection inheritance distinguishes context, target, mutation scope, destination, evidence, and structural hint.
- Structure / Organization remains paused because selection as structural hint could otherwise imply Story Unit persistence.

## Selection As Context Findings

Selection as context means selected material informs another workflow without being the object of direct change.

Safe semantic uses:
- drafting reference
- generation prompt context
- advisory/review context
- advanced analysis input
- verification comparison material

Boundary requirements:
- context selection must not imply the selected text will be replaced
- context selection must not imply permission to include broader scene or project material
- context selection must not become hidden prompt scope without later visibility governance

Risk:
- users may believe a small selection limits blast radius when the system also uses broader context.

## Selection As Target Findings

Selection as target means selected material is the focus of inspection, critique, generation consideration, or rewrite consideration.

Target is narrower than permission:
- a target can be reviewed without being changed
- a target can be inspected without being repaired
- a target can be proposed for rewrite without authorizing apply

Boundary requirements:
- target identity should remain distinct from destination, affected range, and result handling
- target selection must not silently expand to scene, project, or structural scope
- target wording should avoid approval terms

Risk:
- target selection can create a false sense that the user has already consented to the next action.

## Selection As Mutation Scope Findings

Selection becomes mutation scope only after Mutation-Boundary Authority is active.

Required distinction:
- selected source: material being read or transformed
- selected destination: place where changes may land
- affected range: material that may actually change
- supporting context: material used to inform the change but not changed
- blast radius: continuity, persistence, recovery, and downstream effects

Generation and Rewrite / Apply share the overarching mutation-boundary model:
- selection can define generation scope only after target, destination, replacement/addition semantics, and confirmation are clear
- selection can define rewrite/apply scope only after source, candidate result, affected range, and apply behavior are clear

Risk:
- treating selected material as mutation scope before boundary review collapses selection into approval.

## Selection As Destination Findings

Selection as destination means selected location, insertion point, range, scene, or project area receives generated or rewritten material.

Destination is not execution:
- a destination can be chosen without applying content
- a destination can be changed before confirmation
- a destination may require separate review from source material

Boundary requirements:
- destination must be separated from source and context
- replacement destination must be separated from insertion destination
- selected destination should not hide overwritten state or recovery cost

Risk:
- users may interpret destination selection as harmless placement even when it overwrites or reshapes existing draft material.

## Selection Persistence / Expiration Findings

Selection persistence is a governance issue because stale selection can silently carry authority into later states.

Provisional persistence categories:
- `Ephemeral`: expires when focus changes, modal closes, or workflow changes.
- `Session-Bounded`: persists during a bounded review/generation/rewrite flow.
- `Evidence-Bounded`: persists only while inspection or verification evidence remains active.
- `Mutation-Bounded`: persists only through explicit Mutation-Boundary review.
- `Invalidated`: cleared when source material changes, project changes, recovery state changes, or scope becomes ambiguous.

Findings:
- selection should expire or require renewal when changing from advisory to mutation
- selection should expire when verification evidence becomes repair pressure
- selection should not persist into command/search execution routes by default
- stale selection is especially risky for rewrite/apply and recovery-adjacent actions

## Selection Transfer Findings

### Drafting -> Generation

- selection may transfer as prompt context, insertion point, replacement target, or scope hint
- the transfer must identify which meaning is active before generation
- focused drafting legitimacy must not make generation scope feel pre-approved
- generation action remains separate from selected scope

### Drafting -> Rewrite / Apply

- selection may transfer as source text, destination text, affected range, or candidate transformation target
- rewrite/apply requires boundary review because selected source and selected destination may differ
- selected text cannot be treated as apply consent

### Advisory / Review -> Rewrite / Apply

- advisory selection may identify the passage under discussion or the advice being converted
- transition must separate advisory context from mutation target
- accepted advice is not accepted mutation
- candidate rewrite is not apply authority

### Verification -> Repair Pressure

- verification selection may identify evidence, defect area, stale state, report item, or snapshot artifact
- selection of a problem does not authorize repair
- repair pressure should enter Support / Recovery Exception or Mutation-Boundary Authority only if later governed
- recovery restore/reopen governance remains deferred

### Future Command/Search Inheritance Implications

- command/search must know whether selection is context, target, destination, evidence, mutation scope, or structural hint
- search should not convert selected context into command execution target
- command routes must not inherit stale or ambiguous selection
- mutation-capable commands remain unauthorized until selection transfer and mutation-boundary inheritance are stable

## Blast-Radius Interaction Findings

- Target and blast radius are not the same.
- A small selection can have broad blast radius if the action uses scene, project, continuity, recovery, or structural context.
- A broad selection can be inspection-only and have no mutation blast radius.
- Destination can increase blast radius if it overwrites authoritative draft state.
- Selection can reduce ambiguity only when its semantic family is explicit.
- Blast radius must account for persistence, reversibility, recovery cost, continuity effects, and hidden context.

## Multi-Selection / Broad-Scope Risk Findings

- Multi-selection can blur context, target, source, and destination.
- Broad project or scene selection can normalize high-impact mutation as a convenience.
- Multiple selected items can imply batch authority before batch mutation is governed.
- Multi-selection may pressure command/search toward hidden bulk routes.
- Broad-scope selection should not be stabilized before Story Unit pressure reconstruction if it implies structural objects.

## Selection Visibility Findings

- Visible selection creates implied focus but should not create implied permission.
- Persistent selection indicators can normalize stale scope.
- Selection shown near generation or apply controls can create authority adjacency.
- Selection shown near verification can imply repair readiness.
- Selection shown near recovery controls can imply restore target approval.
- Selection vocabulary should avoid words that imply accept, approve, ready, safe, fixed, or apply.

## Highest-Risk Selection Ambiguities

- context versus mutation target
- target versus destination
- selected range versus affected range
- selected evidence versus repair permission
- advisory-selected passage versus apply-ready rewrite
- generation prompt context versus replacement scope
- stale selection versus active user intent
- multi-selection versus batch mutation authority
- broad selection versus Story Unit or topology pressure
- command/search selected item versus executable command target

## Future Command/Search Inheritance Implications

- Command/search must inherit selection semantics from the active workflow context; it must not flatten selection into a generic target.
- Search should remain read-only retrieval unless a later reconstruction pass authorizes routing semantics.
- Command must distinguish selected context, selected target, selected destination, selected evidence, and selected mutation scope.
- Mutation-capable command routes must remain blocked until selection scope, mutation-boundary authority, and workflow-state inheritance are stable.
- Stale, broad, multi-selection, recovery-adjacent, diagnostics-adjacent, and structural selections should not become commandable by default.
- Hidden developer/test, support, recovery, and structure routes must not become discoverable through selected-scope commands.
