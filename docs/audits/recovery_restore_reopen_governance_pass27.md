## Recovery Governance Model

This model is provisional only. It is not implementation authorization, not workflow-state canon, and not final product language.

Recovery governance treats recovery mutation as exceptional authority. Restore and reopen are not ordinary workflow mutation, not harmless navigation, and not repair permission derived from verification.

Provisional recovery semantics:
- `Verification`: proves or reports bounded evidence. It is not repair permission.
- `Inspection`: views state or evidence. It is not recovery.
- `Restore`: uses a prior backup, snapshot, copy, or recovery source to replace or fork current state.
- `Reopen`: returns to or reloads a project/session/state path. It may be navigation, state rehydration, recovery, or replacement pressure depending on context.
- `Repair`: alters state to correct an issue. Repair remains distinct from restore and reopen.
- `Recovery Diagnostics`: exceptional investigation overlay/subfamily under support/recovery, not ordinary diagnostics.
- `Support Visibility`: condition explanation, retry truth, and recovery guidance. It is not recovery normalization.

Recovery mutation requires Mutation-Boundary Authority because it can change source of truth, overwrite user work, fork state, or reshape continuity.

## Executive Findings

- Restore, reopen, repair, verification, and inspection must remain separate semantic families.
- Recovery mutation is exceptional authority and should not normalize into routine workflow maintenance.
- Verification evidence may support recovery decisions, but it does not authorize restore, reopen, or repair.
- Reopen is not harmless navigation by default because it can reload, replace, recover, or reinterpret session/project authority.
- Recovery Diagnostics can support recovery investigation, but it must not become recovery mutation authority or ordinary diagnostics access.
- Future command/search recovery routes remain blocked until restore/reopen governance stabilizes further.
- Recovery blast radius is broader than content change; it includes source of truth, overwrite risk, forked state, stale state, continuity, and user trust in current work.

## Restore Boundary Findings

Restore is exceptional recovery mutation.

Restore boundary questions:
- what source state is being restored
- what current state may be overwritten, forked, or abandoned
- whether restore creates a copy or replaces an authority-bearing project/session path
- whether verification evidence supports the restore source
- what user work may be lost, retained, duplicated, or reclassified
- what post-restore evidence confirms the resulting state

Findings:
- restore must not inherit permission from verification, snapshot presence, or support urgency
- restore must remain separate from snapshot creation and verification/reporting
- restore language should avoid ordinary maintenance framing
- restore must not become a global command/search route

## Reopen Boundary Findings

Reopen is not harmless navigation by default.

Reopen may mean:
- navigate back to a known project
- reload persisted state
- resume a prior session
- recover from incomplete session handoff
- open a recovered copy
- rehydrate state after failure
- resolve stale or missing project state

Boundary questions:
- is reopen navigation, recovery, repair, or state replacement pressure
- what source of truth is being reopened
- whether local unsaved, dirty, stale, or recovered state is affected
- whether reopen changes active project/session authority
- whether reopen should enter Support / Recovery Exception first

Findings:
- reopen should not be treated as neutral when state authority changes
- reopen may need recovery framing when it touches stale, recovered, unsupported, or incomplete project state
- command/search must not expose reopen as generic route until these meanings are separated

## Recovery Mutation Findings

Recovery mutation covers actions that alter state under exceptional conditions.

Examples of recovery mutation pressure:
- restore from backup or snapshot
- restore as copy
- reopen recovered or stale state
- repair missing or invalid state
- replace current project/session authority
- retry operations that change saved or loaded state

Findings:
- recovery mutation requires Mutation-Boundary Authority
- exception state is context, not permission
- urgency is not authorization
- support truth may explain need, not approve action
- diagnostics may inform investigation, not execute recovery mutation

## Verification Versus Recovery Findings

Verification and recovery remain separate.

Verification can:
- inspect
- prove bounded claims
- surface evidence
- identify risk
- inform support truth

Verification cannot:
- repair state
- authorize restore
- authorize reopen
- approve recovery mutation
- imply safety beyond the checked claim

Findings:
- `verified`, `clean`, `valid`, and similar terms require bounded meaning
- verification output may trigger recovery framing but not recovery execution
- inspection evidence must not be presented as repair authority
- verification proximity to restore controls remains a normalization risk

## Recovery Diagnostics Boundary Findings

Recovery Diagnostics remains an exceptional overlay/subfamily under Support / Recovery Exception.

Recovery Diagnostics may:
- collect evidence
- explain recovery conditions
- support handoff to product support or developer investigation
- help distinguish support condition from internal failure

Recovery Diagnostics may not:
- become ordinary diagnostics access
- appear as peer action to restore/reopen
- authorize recovery mutation
- expose developer/test vocabulary to ordinary workflow
- become searchable as a generic command/search route

Findings:
- diagnostics bridge authority must not collapse recovery diagnostics with developer/test diagnostics
- diagnostics folder access remains context-dependent
- recovery diagnostics should exit back to recovery framing or external investigation, not ordinary workflow

## Recovery Exception-State Inheritance Findings

Support / Recovery Exception is the required inheritance context for recovery mutation.

Exception-state inheritance requires:
- current condition that justifies recovery visibility
- bounded support truth explaining why recovery is relevant
- clear separation from ordinary authoring, advisory, inspection, and command/search flows
- Mutation-Boundary Authority before restore, reopen-as-recovery, or repair
- exit back to safe state after condition clears

Findings:
- support/recovery visibility is allowed because of condition, not because recovery is normal workflow
- recovery authority should not leak into Focused Drafting, Advisory / Review, or Verification / Inspection
- unresolved failure may remain support truth without exposing developer diagnostics

## Recovery Visibility / Normalization Findings

Recovery visibility is necessary during real exceptions, but repeated exposure normalizes exception authority.

Normalization pressure arises when:
- restore, reopen, verification, and diagnostics sit in one repeated family
- support/recovery controls remain visible during ordinary workflow
- retry/recovery language becomes part of normal session rhythm
- command/search discovers recovery actions outside exception context
- diagnostics appears beside restore/reopen long enough to feel routine

Findings:
- recovery visibility should be contextual, not ambient
- support visibility must not become recovery normalization
- verification visibility should not drag restore semantics with it
- Recovery Diagnostics should not be visible as an ordinary workflow affordance

## Recovery Command/Search Implications

Recovery command/search routes remain blocked.

Blocked route families:
- restore
- reopen-as-recovery
- repair
- recovery diagnostics
- retry that mutates state
- reveal/open recovered state as authoritative without exception framing

Read-only search may later locate recovery evidence only inside Support / Recovery Exception, but this pass does not authorize it.

Command/search implications:
- recovery routes must distinguish discover, navigate, prepare, preview, inspect, request, and execute
- inspect is not recover
- preview is not restore
- navigation to recovery surface is not restore/reopen authority
- search result visibility is not recovery legitimacy
- global command/search must not surface restore/reopen as ordinary available actions

## Recovery Blast-Radius Findings

Recovery blast radius includes:
- replaced state
- forked state
- overwritten user work
- abandoned current session
- stale or recovered source of truth
- changed project/session authority
- changed recovery evidence
- user trust in current versus restored work
- downstream snapshot, backup, or report meaning

Findings:
- restore blast radius can exceed the visible selected project or snapshot item
- reopen blast radius can include session truth and project authority
- repair blast radius is still ambiguous and should remain separate from restore/reopen
- diagnostics does not reduce blast radius unless it produces bounded evidence for recovery decision-making

## Highest-Risk Recovery Ambiguities

- reopen as navigation versus reopen as recovery mutation
- verification evidence as recovery permission
- inspection as repair
- support visibility as recovery normalization
- recovery diagnostics as ordinary diagnostics access
- retry as support action versus state-changing recovery action
- command/search recovery result as executable authority
- stale state versus recovered state versus current source of truth
- recovery repair versus restore/reopen
