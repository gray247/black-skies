## Entry / Exit Criteria Model

This model is provisional only. It is not final workflow canon, not implementation authorization, and not product navigation.

Entry and exit criteria are classified as:
- `User-Intent Entry`: a user action or explicit workflow intention may enter the family.
- `System-Condition Entry`: runtime, recovery, selection, or state evidence may make the family relevant.
- `Authority-Transition Entry`: a transition from advisory, inspection, selection, or mutation-boundary authority may enter the family.
- `Constraint Entry`: a governing condition applies across another state rather than entering a standalone state.
- `Exception Entry`: recovery/support evidence activates exceptional authority.
- `Dev/Test Entry`: developer or validation context activates non-product diagnostics authority.
- `Completion Exit`: the family exits after work is completed or dismissed.
- `Escalation Exit`: the family exits into mutation, recovery, diagnostics, output, or another authority class.
- `Abort Exit`: the user cancels, closes, or returns to safer authority.
- `Condition-Cleared Exit`: the system condition that justified the family no longer applies.

Entry/exit criteria may later become user actions, system conditions, or mode constraints. They must not be treated here as final requirements, routing logic, GUI structure, or approved implementation scope.

## Executive Findings

- Focused Drafting requires the first entry/exit analysis because it is both a candidate state and a protective governing constraint.
- The riskiest transitions are advisory into mutation, selection into mutation-boundary authority, generation into broad draft mutation, verification into recovery, recovery into diagnostics, and support truth into ordinary workflow tooling.
- Mutation-Boundary Authority should be modeled as a transition governor rather than a normal state.
- Support / Recovery Exception needs broader entry/exit framing before Recovery Diagnostics can stabilize.
- Diagnostics / Developer-Test remains dev/test-only or hidden/internal for normal product use.
- Structure / Organization entry/exit remains provisional because Story Unit pressure reconstruction has not happened.
- Command/search remains deferred until entry/exit criteria exist and authority inheritance can be reconstructed.
- Export / Output remains excluded from state candidates through this pass and should be treated as an authority class only.

## Focused Drafting Entry / Exit Findings

Focused Drafting is analyzed first because it has two roles:
- `State Candidate`: a protected primary authoring context.
- `Constraint Candidate`: a governing rule that limits authority compression across other states.

Provisional entry criteria as state:
- user enters or resumes draft writing
- a project or scene is open with writing as the primary intent
- non-writing surfaces are dismissed, inactive, or contextually secondary
- no active recovery exception requires interruption
- no mutation-boundary transition is currently being confirmed

Provisional exit criteria as state:
- user explicitly enters selection, review, generation, rewrite/apply, verification, support/recovery, analysis, or structure work
- system enters a recovery/support exception that must interrupt drafting
- user opens an authority-bearing surface that changes primary intent
- mutation target/scope/confirmation becomes the active task
- drafting is completed, paused, or abandoned

Provisional entry criteria as constraint:
- any workflow still presents writing as the primary user goal
- any adjacent non-writing authority risks visual equivalence with writing
- any support, diagnostics, status, command/search, analysis, or recovery surface would compete with authoring authority

Provisional exit criteria as constraint:
- later canon identifies a workflow state where writing is not primary and no drafting protection is needed
- an exception state temporarily overrides drafting protection with explicit recovery/support framing
- a mutation-confirmation state intentionally displaces drafting under explicit boundary rules

Primary risk:
- If Focused Drafting exits too easily, the product becomes a mixed-authority dashboard.
- If Focused Drafting cannot exit, necessary review, verification, generation, and recovery work becomes awkward or hidden.

## Selection / Capture Entry / Exit Findings

Provisional entry criteria:
- user selects text, scene material, project material, or a target region
- system receives an explicit capture intent without approving mutation
- another state requests a target before advisory, inspection, generation, rewrite/apply, structure, or output work

Provisional exit criteria:
- selection is cleared, replaced, or expires
- selected material becomes an inspection target
- selected material becomes advisory context
- selected material enters mutation-boundary authority for generation or rewrite/apply
- selected material becomes output/export scope under a separate authority class

Boundary finding:
- Selection / Capture should not imply approval, readiness, scope consent, or mutation permission.

Highest risk:
- selected scope can feel like approved scope before target, blast radius, and confirmation are explicit.

## Generation Entry / Exit Findings

Provisional entry criteria:
- user explicitly requests new or replacement draft material
- a mutation target and scope are available or must be requested
- Mutation-Boundary Authority is invoked before draft-changing generation
- service/runtime truth may explain availability but must not grant permission

Provisional exit criteria:
- generation result is produced without automatic apply, if later canon requires review
- user accepts, rejects, revises, or abandons the result
- generation escalates into Rewrite / Apply or another mutation-bearing transition
- service failure exits into bounded support truth, not diagnostics leakage
- user returns to Focused Drafting or Advisory / Review

Boundary finding:
- Generation should enter through explicit intent and mutation-boundary governance, not through ambient availability or command/search convenience.

Highest risk:
- generation can become normalized broad mutation if entry is always visible and exit does not force review, target clarity, or blast-radius awareness.

## Rewrite / Apply Entry / Exit Findings

Provisional entry criteria:
- advisory or review output proposes a change
- user requests transformation of existing material
- a saved rewrite, diff, or preview exists as a candidate change
- Mutation-Boundary Authority identifies target, scope, and apply behavior

Provisional exit criteria:
- user applies the change under explicit confirmation
- user rejects, closes, or discards the candidate change
- user returns to Advisory / Review without mutation
- user returns to Focused Drafting after apply or dismissal
- apply failure exits into support truth or recovery only if an exception condition exists

Boundary finding:
- Rewrite / Apply must make the transition from advice to mutation visible.

Highest risk:
- advisory legitimacy can transfer into mutation if apply controls appear as a natural continuation of critique or review.

## Mutation-Boundary Authority Transition Findings

Mutation-Boundary Authority is provisionally a transition governor, authority class, and constraint candidate, not a normal workflow state.

Provisional entry criteria:
- any operation can alter draft content, project state, recovery state, structure, output records, or other persistent authority-bearing state
- selection or advisory material is about to become mutation scope
- default target/scope would otherwise imply silent approval

Provisional exit criteria:
- target, scope, confirmation, and blast radius are accepted and mutation proceeds
- mutation is cancelled or abandoned
- boundary evidence is insufficient and the transition returns to the prior safer state
- user changes scope and re-enters boundary review

Boundary finding:
- Mutation-Boundary Authority should govern Generation, Rewrite / Apply, recovery restore, structure mutation, and possibly export side effects without becoming a routine setting.

Highest risk:
- compact controls or defaults can hide blast radius while appearing to satisfy governance.

## Advisory / Review Entry / Exit Findings

Provisional entry criteria:
- user requests critique, review, interpretation, guidance, or recommendations
- selected or current draft material becomes advisory context
- inspection evidence is interpreted without direct repair

Provisional exit criteria:
- user returns to Focused Drafting
- user enters Rewrite / Apply or Generation through explicit mutation-boundary transition
- user dismisses advisory content
- advisory work exits into Verification / Inspection if evidence must be checked
- advisory work pauses during Support / Recovery Exception unless later canon permits bounded support advice

Boundary finding:
- Advisory / Review should not exit directly into mutation without a visible authority transition.

Highest risk:
- advice becomes pseudo-permission when near apply, generate, or command surfaces.

## Verification / Inspection Entry / Exit Findings

Provisional entry criteria:
- user requests proof, validation, report review, state inspection, or verification
- system presents evidence needed before mutation, restore, export, or recovery
- support condition requires inspection evidence without developer diagnostics

Provisional exit criteria:
- user returns to the prior workflow with evidence understood as evidence only
- inspection reveals an exception and enters Support / Recovery Exception
- inspection evidence informs Advisory / Review without becoming advice itself
- inspection evidence becomes output/report authority without implying readiness
- user dismisses or abandons inspection

Boundary finding:
- Verification / Inspection proves bounded claims. It must not imply repair, safety, approval, readiness, or recovery permission.

Highest risk:
- inspection can collapse into recovery if report, restore, snapshot, and support controls are adjacent.

## Support / Recovery Exception Entry / Exit Findings

Provisional entry criteria:
- a failure, degraded condition, stale state, missing resource, recovery-required condition, restore need, reopen problem, or support condition interrupts ordinary workflow
- user explicitly requests recovery/support for an exceptional condition
- verification/inspection detects evidence that requires recovery framing
- runtime truth explains a condition without becoming ordinary readiness inference

Provisional exit criteria:
- condition is resolved and user returns to Focused Drafting or the prior safe state
- user cancels recovery and returns to a non-mutating state
- recovery mutation completes with clear boundary and result evidence
- unresolved failure remains in support truth without exposing developer diagnostics
- Recovery Diagnostics is entered only after support/recovery framing exists

Boundary finding:
- Support / Recovery Exception must remain exceptional, contextual, and condition-bound.

Highest risk:
- repeated or always-visible recovery affordances can normalize exception authority into ordinary maintenance workflow.

## Recovery Diagnostics Entry / Exit Findings

Recovery Diagnostics is treated as an exceptional overlay/subfamily under Support / Recovery Exception, not a normal state.

Provisional entry criteria:
- Support / Recovery Exception is already active
- recovery investigation requires bounded diagnostic evidence
- product-support or recovery-facing condition language can frame the investigation without developer/test vocabulary leakage
- diagnostics access is context-dependent and justified by the exception

Provisional exit criteria:
- diagnostic evidence is collected, viewed, or handed off
- user returns to Support / Recovery Exception
- issue is resolved and exits to prior safe state
- investigation crosses into developer/test context and leaves ordinary product workflow
- diagnostic path is unavailable and support truth explains the condition without exposing internal terms

Boundary finding:
- Recovery Diagnostics may support recovery investigation, but it must not borrow restore/reopen mutation authority or become routine diagnostics access.

Highest risk:
- `View diagnostics` near restore/reopen reads as a peer recovery action unless audience and context are explicit.

## Diagnostics / Developer-Test Entry / Exit Findings

Diagnostics / Developer-Test is treated as a dev/test-only workflow state or hidden/internal infrastructure for normal product use.

Provisional entry criteria:
- developer/test environment, validation scaffold, harness, forced status, internal log investigation, or explicitly non-product diagnostic context is active
- operator/product support has escalated to developer investigation outside ordinary workflow
- internal reason keys or test-state semantics are needed for engineering analysis

Provisional exit criteria:
- developer/test investigation ends
- evidence is translated into product-support condition language before any operator exposure
- forced or test state is cleared
- ordinary product workflow resumes without dev/test surfaces

Boundary finding:
- Diagnostics / Developer-Test should never be entered by ordinary user visibility, advanced-user affordance, command/search discovery, or ambient support placement.

Highest risk:
- developer precision can become product authority if internal terms appear in rendered workflow surfaces.

## Advanced Analysis Entry / Exit Findings

Provisional entry criteria:
- user requests deeper analysis, interpretation, comparison, context, or intelligence support
- advisory, inspection, or structure evidence requires deeper synthesis
- selected material or project context is analyzed without direct mutation

Provisional exit criteria:
- user returns to Focused Drafting, Advisory / Review, or Verification / Inspection
- analysis recommends mutation and must transition through Advisory / Review plus Mutation-Boundary Authority
- analysis becomes structural and may defer to Structure / Organization after Story Unit pressure reconstruction
- analysis is dismissed or converted into output evidence under Export / Output authority

Boundary finding:
- Advanced Analysis may be advisory, inspection-like, or structural, but it should not become dashboard authority or quality certification.

Highest risk:
- analysis surfaces can imply judgment, certainty, or readiness when vocabulary, status, and evidence are not bounded.

## Structure / Organization Entry / Exit Findings

Structure / Organization remains provisional and dependent on later Story Unit pressure reconstruction.

Provisional entry criteria:
- user requests navigation, organization, grouping, ordering, outlining, or structural review
- selection/capture identifies structural material without authorizing persistence
- advanced analysis proposes structural interpretation

Provisional exit criteria:
- user returns to Focused Drafting or Advisory / Review
- structural view remains read-only and is dismissed
- a structural mutation is requested and must wait for Story Unit pressure reconstruction plus Mutation-Boundary Authority
- structural output is exported under Export / Output authority without implying Story Unit persistence

Boundary finding:
- Structure / Organization cannot stabilize until the unit of structure, persistence implications, topology pressure, and mutation authority are reconstructed.

Highest risk:
- structure vocabulary can silently authorize Story Unit persistence or topology architecture.

## State Boundary Risks

- Entry through visibility: a visible control can imply the state is available, legitimate, or recommended.
- Entry through adjacency: support, diagnostics, recovery, inspection, advisory, and mutation controls can borrow each other's authority.
- Entry through repetition: repeatedly visible exceptional paths become normalized.
- Exit ambiguity: users may believe they are still in advisory or inspection while a mutation state has started.
- System-condition ambiguity: runtime truth can trigger support framing while being mistaken for readiness approval.
- Overlay ambiguity: diagnostics, recovery diagnostics, advanced analysis, status/truth, and command/search can appear over states without clear inherited authority.
- Constraint ambiguity: Focused Drafting and Mutation-Boundary Authority may govern states without being states themselves.
- Authority-class ambiguity: Export / Output can appear inside states without being a state candidate.

## Highest-Risk Entry / Exit Ambiguities

- When Focused Drafting exits versus when it continues as a protective constraint.
- When Selection / Capture becomes mutation-boundary authority.
- When Advisory / Review becomes Rewrite / Apply.
- When Generation enters as bounded mutation rather than ordinary writing convenience.
- When Verification / Inspection becomes Support / Recovery Exception.
- When Support / Recovery Exception may expose Recovery Diagnostics.
- When Recovery Diagnostics becomes developer/test diagnostics.
- When Advanced Analysis is advisory, inspection, structural, or output authority.
- When Structure / Organization implies Story Unit persistence.
- When command/search may later enter, route, or execute state transitions.

## Contradictions Found

- Focused Drafting must be easy to protect but cannot block necessary transitions into review, generation, verification, or recovery.
- Selection / Capture is often harmless by itself but can silently define mutation blast radius.
- Generation is central to product value but must enter through mutation-boundary governance.
- Rewrite / Apply depends on advisory context while requiring a visible exit from advisory authority.
- Verification / Inspection needs evidence visibility, yet evidence visibility can imply readiness or permission.
- Support / Recovery Exception must interrupt ordinary workflow when needed, yet interruption visibility can normalize exception tooling.
- Recovery Diagnostics needs access from recovery context, yet diagnostics access must stay outside ordinary workflow.
- Structure / Organization is likely needed, but stabilizing it before Story Unit pressure reconstruction risks authorizing persistence by vocabulary.
