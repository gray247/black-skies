# Stage 11 Fatal Question Review Program

## Status

- Stage 11 is active for read-only planning and bounded question review.
- Implementation remains blocked.
- Stage 11 may use additional review, correction, or contradiction-resolution passes whenever the evidence requires them; no fixed pass count limits the review.
- This program record defines the review before later Stage 11 batches are created.

## Purpose

Stage 11 exists to decide whether the current architecture contains a structural contradiction, ownerless critical responsibility, hidden truth-mutation path, unsafe workflow collapse, or readiness claim that cannot be contained by the present doctrine and ownership model.

Stage 11 does not answer implementation details. It decides whether a question is fatal to the current architecture sequence, whether it is only a serious operational risk, whether it is a normal author decision, or whether it belongs in later stages.

## Fatal Question Definition

A Fatal Question is a question whose answer could reveal that the architecture, governance model, or ownership structure is internally contradictory or structurally unable to satisfy its core purpose.

A Fatal Question is not:

- an ordinary unresolved feature detail
- a missing implementation proof
- a later test case
- an implementation mechanic
- a library or schema choice
- a defect that can be handled by later coding alone

## Authority and Boundary

- Author authority remains final.
- AI remains advisory until explicitly accepted.
- Analysis may be automatic; truth mutation remains manual.
- Stage 11 may classify questions, identify risks, and route unresolved architecture questions, but it does not authorize implementation.
- Stage 12 remains separate and begins only after Stage 11.

## Approved Batches

Stage 11 uses five approved batches:

1. Truth, authority, and cross-system ownership
2. Data integrity, save, recovery, and migration
3. AI routing, approval, provenance, and transmission
4. Queue, service failure, performance, cost, hardware, and model lifecycle
5. Accessibility, packaging, deployment, and release evidence

Batch 1 comes first because a contradiction in truth or ownership can invalidate the rest of the sequence.

## Severity Taxonomy

Use only these severities:

- fatal architecture blocker
- severe architecture risk
- serious operational risk
- ordinary unresolved author decision
- later implementation-proof obligation
- Stage 12 architecture dependency
- not a Fatal Question

## Verdict Taxonomy

Use only these verdicts:

- ruled out by current doctrine
- ruled out by cross-document synthesis
- confirmed structural contradiction
- unresolved and must be corrected in Stage 11
- genuine author decision
- deferred to Stage 12 with named trigger
- deferred to later implementation proof with named evidence requirement
- rejected as not a Fatal Question

A verdict must not claim runtime proof unless there is bounded observed runtime, harness, packaged-application, or test execution evidence.

## Evidence Requirements

Each question needs:

- the exact question
- the current owner or authority implicated
- direct doctrine that bears on it
- cross-document evidence that supports or challenges it
- a contradiction search across the relevant records
- a verdict and severity
- any genuine author decision, Stage 12 dependency, or later implementation-proof obligation
- a reopening trigger if the verdict later changes
- the consequence if the verdict changes

Evidence may come from doctrine, workflow-proof records, ownership matrices, and cross-document synthesis. It may not be overstated as live operational proof unless current bounded execution evidence exists.

## Doctrine-Resolved Versus Cross-Document Questions

- Doctrine-resolved questions are already decided by explicit current doctrine.
- Cross-document questions require comparing multiple records to confirm that no hidden ownership or authority contradiction exists.
- If doctrine and cross-document synthesis both settle the question, Stage 11 records the issue as not fatal and does not defer it.

## Author-Decision Handling

Record a genuine author decision only when:

- doctrine does not already decide the matter
- the question materially affects architecture or ownership
- the choice is not just an implementation detail

Do not turn every threshold, preference, or later proof need into a Fatal Question.

## Deferral Rules

A question may be deferred only when:

- Stage 11 genuinely lacks authority or evidence to answer it
- the receiving stage is explicitly named
- the reopening trigger is explicit
- the deferral does not hide a structural contradiction

Later implementation proof may receive proof obligations only after the architecture is judged coherent.

## Reopening Triggers

Reopen a question only if a later record shows one of the following:

- a contradiction in current doctrine
- a conflict between ownership records
- a truth-mutation path without explicit author acceptance
- a hidden universal owner or mandatory workflow gate
- a later Stage 12 architecture issue that changes the question's status
- bounded current execution evidence that contradicts the present verdict

## Stage 12 Handoff Rules

Stage 12 receives only genuine architecture or ownership questions.

Every Stage 12 handoff must state:

- the exact unresolved question
- why Stage 11 cannot answer it
- the receiving stage
- the reopening trigger
- the consequence if unresolved

Stage 12 is not a dumping ground for ordinary missing evidence.

## Verdict-Matrix Plan

Stage 11 will maintain a verdict matrix that records, for each question:

- question text
- domain
- severity
- verdict
- owner/authority
- evidence basis
- contradiction search result
- unresolved decision or deferral target
- reopening trigger
- consequence if the verdict changes

The verdict matrix must stay separate from the program record and from later closure records.

## Closure Criteria

Stage 11 may close only when:

- every Fatal Question has a verdict
- every fatal blocker is resolved, rejected, or explicitly carried into Stage 12
- no critical contradiction is hidden as an ordinary decision
- no ownerless critical responsibility remains unnamed
- every deferral names a receiving stage and reopening trigger
- Stage 12 receives a precise architecture-readiness input set
- implementation remains blocked until the later readiness stages complete

## Unsupported Scope

Stage 11 does not include:

- implementation work
- runtime code changes
- test creation or execution
- schema, API, library, provider, or deployment decisions
- connector admission
- truth mutation
- Stage 12 execution
- the verdict matrix itself
- the closure record itself
