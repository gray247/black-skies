## 4. Vertical slice purpose

Purpose:

- define the first buildable Black Skies vertical slice as a planning record only
- establish a minimal project-open, truth/authority, two-surface, narrow writing-flow, and status-flow spine

This plan does not authorize implementation.

## 5. Vertical slice definition

The vertical slice is:

A minimal buildable spine proving Black Skies can open a project, preserve project truth/authority, expose the two-surface workflow, and support one narrow writer-facing flow without broad feature expansion.

## 6. Included spine

Required included spine:

1. `Project context opens`
   The user can open into one selected or active project context.
2. `Project truth/identity is visible`
   The user can see which project is active and basic authority/status identity.
3. `Two-surface shell is visible`
   `Writing Surface` and `Command Center` are both present as separate surfaces.
4. `Writing Surface supports narrow manuscript/prose work`
   The user can view or enter narrow manuscript/prose text in the writing surface.
5. `Command Center supports minimal project/status awareness`
   The user can see minimal project/status/control context without mutating manuscript truth.
6. `Save-state/status is visible`
   The user receives a clear signal about save/state/status for the narrow writing flow.
7. `Excluded systems remain excluded`
   The slice does not require excluded systems to appear functional.

## 7. Excluded systems

Excluded systems:

- restore/import behavior
- sample-root/protected-evidence path dependence
- `External Challenge / Current Validation` substance
- broad AI generation
- critique system
- rewrite loop
- export/import pipeline
- advanced diagnostics
- connector work
- cleanup/archive execution
- snapshot/witness regeneration
- broad test-suite stabilization
- packaging polish
- theming/polish beyond minimal two-surface visibility

## 8. Visible-but-non-mutating systems

Visible but non-mutating systems:

- project truth/authority indicators
- save-state/status messaging
- Command Center support context

These may be visible only to support orientation, status, and authority understanding.
They must not silently mutate project truth, manuscript truth, or accepted author content.

## 10. Truth/authority boundary

Truth/authority boundary:

- the slice must show active project identity/truth authority
- the slice must not regenerate truth
- the slice must not silently change project authority
- the slice must not mutate manuscript truth from the Command Center
- author/manual acceptance remains the truth mutation boundary

## 11. Two-surface workflow boundary

Two-surface workflow boundary:

- `Writing Surface` and `Command Center` remain distinct
- `Writing Surface` is for narrow manuscript/prose work
- `Command Center` is for minimal project/status/control awareness
- analysis/control surface must not silently mutate creative text

## 12. Writer-facing flow boundary

Required writer-facing flow:

1. a user can open a project context
2. the user can see which project is active
3. the user can see both surfaces
4. the user can enter or view narrow manuscript/prose content
5. the user can see save-state/status feedback
6. the user can complete the flow without excluded systems

## 13. Save-state/status boundary

Save-state/status boundary:

- one narrow save-state/status flow is visible to the writer
- the status signal must be understandable enough for the first slice
- the slice does not require full backup/restore, snapshot regeneration, broad history tooling, or degraded/recovery doctrine completion
