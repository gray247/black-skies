## 2. Purpose

Define Memory Lab as Black Skies' governed memory and recall system
without letting it silently become a truth owner, a search system, or a
shadow database for manuscript, project, character, lore, note, signal,
Binder, or Series Binder truth.

Memory Lab is centered on:

- author reminders,
- decision and rationale history,
- Companion guidance,
- references to truth owned elsewhere,
- series and cross-project context,
- temporary session context.

Memory Lab must remain fully useful without AI.
It is not the normal human document export path, and temporary AI
package payloads are not the same thing as durable Memory Lab records.

This dossier inherits durable-state ownership from
`truth_and_state_ownership_matrix.md`, AI conversion and retention
limits from `ai_lifecycle_and_approval_matrix.md`, protection rules
from `protected_content_permission_matrix.md`, advisory vocabulary from
`shared_output_vocabulary_contract.md`, provenance posture from
`provenance_state_model.md`, degraded behavior from
`degraded_mode_execution_contract.md`, recovery posture from
`snapshot_protected_recovery_contract.md`, and document-boundary
doctrine from `document_interchange_source_destination_contract.md`.

## 3. User Problem Solved

Writers need a governed memory layer that can retain meaningful,
approved recall with evidence and provenance, carry reminders and
decision history across projects, and support `Companion` without
pretending remembered material is automatically current canon or
accepted truth.

## 4. What The System Does

- owns governed durable memory records,
- owns recall state, approval state, retention state, archive state,
  forgetting state, deletion state, and provenance state for those
  records,
- retains approved memory that supports reminders, decisions,
  continuity, memory, structure, investigation, or author decision
  support,
- preserves source labels, memory class, scope, provenance, and
  protection posture,
- provides project-scoped durable recall,
- provides series and cross-project context only when explicitly shared
  into scope,
- provides bounded temporary session context without confusing it with
  durable memory,
- supports author-controlled archive, forget, restore, detach, and
  delete-memory actions,
- supports multiple downstream systems.

Memory Lab owns memory-record state only.
It does not own the accepted truth that those records may reference.

## 5. What The System Does Not Do

- it is not simple storage,
- it is not automatic truth owner,
- it does not silently rewrite story material,
- it does not replace author judgment,
- it does not let memory candidates silently become durable memory,
- it does not turn repeated viewing, search, retrieval, generation, or
  inference into memory,
- it does not own `Companion`, `Critique`, `Continuity`,
  `Signal Architecture`, `Feedback Notes`, `Project Index / Search /
  Retrieval`, `Binder / Project Library`, or `Series Binder /
  Cross-Story Linking`,
- it does not silently share memory across projects or Story Chains.

## 6. User-Facing Behavior

Memory Lab may later appear as an inspectable governed-recall layer,
author reminder system, decision-history layer, source-backed memory
store, or evidence-backed assistant capability.
Any later recall exposed through `Companion` should preserve memory
class, scope, and source labels rather than flattening everything into
apparent canon.

## 20A. Product Identity

Memory Lab is a combined governed memory system centered on:

- author reminders,
- decision and rationale history,
- Companion guidance,
- references to truth owned elsewhere,
- series and cross-project context,
- temporary session context.

It must remain fully useful without AI.
It is not a universal truth owner, universal search layer, or silent
cross-project sharing engine.

## 20B. Memory Classes And Identity

Memory Lab should explicitly distinguish these classes:

- `personal author memory`
- `author-approved advisory memory`
- `owner-reference memory`
- `approved-summary memory`
- `decision or rationale memory`
- `Companion-guidance memory`
- `global author preference`
- `project override`
- `temporary session context`
- `rejected candidate`
- `stale memory`
- `superseded memory`
- `conflicted memory`
- `restricted memory`
- `archived memory`
- `forgotten memory`
- `deleted memory`
- `inaccessible-source memory reference`

`personal author memory` is a memory record the author enters and keeps
in Memory Lab without automatically promoting it to project truth.

`author-approved advisory memory` is non-canon support material the
author explicitly saves for later governed recall.

`owner-reference memory` points at accepted truth or other owner-held
state without duplicating ownership.

`approved-summary memory` stores a bounded author-approved summary,
especially where raw source material is protected, excluded, too large,
or intentionally not retained in full.

`decision or rationale memory` records what was decided, why it was
decided, and any optional bounded rationale that explains later choices.

`Companion-guidance memory` is author-approved retained guidance useful
for later `Companion` explanation without turning that guidance into
truth ownership.

`global author preference` is reusable author memory that applies
across projects unless a narrower scope overrides it.

`project override` is a narrower project-specific memory that overrides
broader preference or shared guidance for that project only.

`temporary session context` remains bounded context for immediate
workflow help and is not durable memory by default.

`rejected candidate` is a proposed memory that was not approved for
durable retention.

`stale`, `superseded`, `conflicted`, `restricted`, `archived`,
`forgotten`, `deleted`, and `inaccessible-source` are memory-record
postures, not truth-owner mutations.

Each memory record needs its own durable identity.
That identity must not replace source identity, truth-owner identity,
search-result identity, Binder identity, or Story Chain identity.

## 20C. Capture And Inbox Model

Default capture posture is a quick `Remember this` action from
author-facing contexts, followed by lightweight classification.

Required initial classification is:

- memory type
- scope

Incomplete items may enter a temporary review inbox.
Inbox presence is not durable approval by itself.

Durable memory may be created only through explicit governed paths such
as:

- direct author entry,
- explicit save from `Project Index / Search / Retrieval`,
- approved `Companion` suggestion,
- approved note conversion,
- approved signal conversion,
- source-owner reference capture,
- post-import approval,
- author-approved summary capture.

Nothing becomes durable memory merely because it was:

- viewed,
- searched,
- retrieved,
- generated,
- inferred,
- detected,
- suggested.

Repeated explicit author decisions may generate a quiet candidate
suggestion later.
AI inference alone is insufficient.

Every suggestion should show:

- trigger
- source
- proposed scope
- consequence of acceptance

## 20D. Direct Author Memory And Truth Routing

Direct author entry may remain in Memory Lab without automatically
becoming `Author Intent / Story Setup`.

When direct author entry resembles broader project truth, canon, or
durable editorial truth, Memory Lab should ask whether it should:

- remain `personal or advisory memory`
- route to `Author Intent / Story Setup`
- route to `Character Cards`
- route to `Lore Cards`
- route to `Narrative Insertion / Narrative Assertion`
- route to `Outline` or `Story Unit`
- route to `Feedback Notes / Revision Resolution` or
  `Signal Architecture`

Memory Lab must never route automatically.

Rejected ideas may remain archived with rationale and stay out of
ordinary recall.
Decision-change rationale is optional but encouraged.

## 20H. Provenance Model

Minimum provenance for a durable memory record should include:

- memory identity,
- memory class,
- scope,
- source owner,
- source identity,
- source anchor,
- source revision,
- creation method,
- approving author action,
- approved-summary status,
- protection labels,
- owner transfer history,
- stale or conflict posture,
- archive, forget, detach, and delete events,
- influence history later where bounded explanation is useful.

Provenance explains why the memory exists, how it was approved, what it
refers to, where it came from, and whether it remains trustworthy as
recall.
It does not become source truth or owner authority on its own.

## 20I. Source Deletion And Missing-Source Behavior

Memory Lab should use explicit missing-source posture.

Settled model:

- reference-only memory becomes a tombstoned reference when the source
  disappears,
- approved bounded-summary memory may survive as archived detached
  advisory memory,
- surviving memory must clearly state that the source is missing,
  deleted, inaccessible, or detached,
- no surviving memory may pretend to remain current source truth,
- deleted source content must not be reconstructed silently,
- upstream source deletion remains separate from memory deletion.

When upstream truth changes, Memory Lab should:

- preserve bounded history,
- create or link the new current reference,
- mark old memory stale or superseded,
- avoid silently rewriting history.

Leaving or archiving a Story Chain removes its memories from active
project recall but preserves historical linkage.

## 20J. Lifecycle

Memory lifecycle posture should remain explicit:

- `candidate`
- `approved`
- `active`
- `stale`
- `superseded`
- `conflicted`
- `restricted`
- `expired`
- `archived`
- `restored`
- `forgotten`
- `deleted`

`candidate` is proposed memory not yet retained durably.
`approved` means the record passed the relevant author-governed save
path.
`active` means it remains available for ordinary governed recall.
`stale` means the source, source anchor, source revision, protection
state, or broader context may no longer match current reality.
`superseded` means a newer memory or source state displaced it without
erasing provenance.
`conflicted` means the memory record and current source evidence or
other approved memory cannot be presented as one settled context.
`restricted` means protection or visibility limits narrow or block
ordinary recall.
`expired` means the record is no longer worth active surfacing.
`archived` means preserved and recallable but demoted.
`restored` means an archived memory returned to active governed review
or use.
`forgotten` means removed from active recall without deleting upstream
truth.
`deleted` means the Memory Lab record itself was removed.

## 20K. Archive, Forget, Delete, And Detach

These actions are distinct:

- `archive`: preserved and recallable, but demoted
- `forget`: removed from active recall
- `delete memory record`: removes the Memory Lab record
- `detach source`: removes or tombstones the source link while
  preserving allowed memory residue
- `delete upstream truth`: handled by the source owner
- `purge protected raw content`: removes disallowed retained content
  without implying source deletion

`Forget this` should offer scope such as:

- current project
- selected projects
- Story Chain
- entire memory record

Forgotten memories move to a dedicated recoverable view and do not
participate in ordinary recall.
Archive remains recallable but demoted.
Conflict prevents use as settled context.
Superseded but historically useful memory may remain archived with
rationale.

Forgetting must not delete upstream truth.
Deleting a Memory Lab record must not delete upstream truth.
Detaching a source link must not invent new truth or hide that the
source is gone.

## 20M. Recall Behavior

Recall should distinguish:

- manual recall,
- Companion-assisted recall,
- project-scoped durable recall,
- workspace or session temporary context,
- source labels,
- uncertainty,
- stale or conflict labels,
- restricted recall,
- bounded active context,

Manual recall is explicit author-facing retrieval of governed memory.

Project-scoped durable recall is distinct from workspace or session

Stale and conflicted memories remain quiet by default but summonable and

Recall prominence should remain bounded and relevance-driven.
This dossier does not define ranking algorithms or token budgets.

## 20N. Search Versus Memory Lab

`Project Index / Search / Retrieval` finds current source-linked
material.
`Memory Lab` retains explicitly governed durable recall.

Search results require explicit save to become memory.
Saved memory preserves provenance, source labels, memory class, scope,
and protection labels.
Search history is not memory.
Memory may point back to searchable sources.
Missing, deleted, restricted, stale, or moved sources change recall
posture rather than silently disappearing or remaining current.

Memory Lab should avoid vague wording such as `indexed evidence` or
`retrieval structures` when that implies search ownership.
Its durable structures are memory records, recall posture, provenance,
approval state, and retention state.

## 20O. Companion And AI Behavior

Governed Memory Lab actions later may include:

- `Remember this`
- `Save this as advisory memory`
- `Save this as personal memory`
- `Promote through the correct owner`
- `Show source`
- `Explain why this is stale`
- `Forget this`
- `Archive this`
- `Delete this memory record`

`Companion` may expose those actions, but it does not own their result.
It must preserve memory class, source labels, protection posture,
scope, and approval state.

AI or Companion suggestions remain candidates until approved.
AI inference does not become durable memory without explicit approval.
AI-generated replacement summaries require explicit author review.

For every AI request, Memory Lab should support:

- a concise included-memory summary with expandable detail,
- temporary per-request exclusion,
- automatic relevance selection only with visible preview,
- global pins only when relevant,
- only project-shared series memory by default,
- a short inclusion reason per memory.

When memory conflicts with source truth:

- exclude and warn by default,
- allow deliberate comparison mode with both sides clearly labeled.

Local-only memory may be used by genuinely local models.
Never-send memory is excluded from outbound use.
Memory Lab should record bounded influence history.

## 20P. Protection And Degraded Behavior

Memory Lab must apply explicit protection rules for:

- approved-summary memory versus raw content,
- protected or deleted sources,
- masked and excluded content,
- local-only and never-send,
- source previews,
- incomplete deletion,
- corrupt memory records,
- stale anchors,
- unavailable AI,
- conflicting records.

Memory Lab must not leak restricted content through recall, summaries,
`Companion`, exports, or AI packages.
Approved-summary memory may be retained where raw content is not.
Raw masked or excluded spans are not stored by default.
Source previews must degrade to safe metadata, approved summary,
restriction reason, or no preview when protection requires it.

Memory failure must not block writing or ordinary project access.
Corrupt records, incomplete deletion, unavailable sources, unavailable
AI, or stale anchors must fail honestly and preserve safe local work.

## 24. Model Routing Notes And Cost / Budget Impact

Memory Lab is a likely heavy user of routing and budget policy.
It should not assume deep paid runs by default.
Retention policy must respect relevance, performance, and storage-cost
discipline.
Some Memory Lab work may be better as scheduled, idle, or overnight
local work when local analysis is slow but free.
Any silent scheduled work must remain local-only, free,
non-destructive, advisory, non-outbound, non-mutating, and protection
safe.
`Memory Lab` should prefer the cheapest safe source of context first:
accepted doctrine, saved project metadata, governed recall, existing
signals, then prepared findings before heavier scans.
Rough workload tiers for later Memory Lab participation are:

- instant existing-context lookup,
- lightweight local scan,
- idle or deferred local analysis,
- scheduled or overnight local analysis,
- manual heavy scan,
- paid or outbound approved work.

No full-project, local-LLM, paid, outbound, destructive, or
durable-state-changing Memory Lab work may run silently.
No full-project scan should run on every save, and no heavier scan
should run while the author is actively typing unless it is cheap,
local, and non-disruptive.

- `restricted memory`
- `archived memory`
- `forgotten memory`
- `deleted memory`
- `inaccessible-source memory reference`

These are rough product-definition boundaries, not a final storage
schema.
Memory Lab must preserve the difference between canon, advisory memory,
temporary context, archive reference, detached source posture, series
context, and scoped preference.

Risks:

- fake omniscience,
- overreach into canon,
- hidden storage sprawl,
- evidence-free accusations,
- stale or detached memory being mistaken for current truth,
- silent cross-project bleed that reads like shared canon.

## 29. Failure Modes

- Memory Lab mistakes draft for canon,
- Memory Lab cites weak evidence,
- Memory Lab becomes too noisy or too quiet,
- Memory Lab stores things the writer expects to disappear,
- Memory Lab presents missing-source memory as if it were current,
- Memory Lab leaks protected summaries or stale source detail,
- Memory Lab makes series context appear automatically shared when it
  was not explicitly shared.

## 30. v1 Boundary

Doctrine only plus explicit memory classes, provenance boundaries,
retention boundaries, source-deletion posture, scope and Story Chain
posture, AI package inclusion rules, and recall or forgetting
boundaries.

## 31. v2 Boundary

Bounded investigative workflows, explicit evidence inspection, stronger
stale-memory review, clearer downstream integrations, and better series
inspection views.

## 32. Future-Only Boundary

- automatic truth ownership,
- silent rewrite,
- hidden persistence expansion without policy,
- default heavy paid investigation loops,
- invisible durable memory creation from repeated search or retrieval,
- automatic Story Chain creation or automatic cross-project sharing.
