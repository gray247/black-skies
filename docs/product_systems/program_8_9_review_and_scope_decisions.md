### Owner and lifecycle contract details

The first accepted-fact contract needs more precision than `authority: advisory | accepted` plus a generic lifecycle enum:

- Stable project/entity/fact identity and schema version; typed payload, current fact revision and links to superseded revisions.
- Distinguish acceptance, evidence freshness, dispute/planning posture, active/archive/deletion state and protection. An accepted fact with stale evidence is not automatically revoked or replaced. A candidate being stored does not make it accepted.
- Separate author-known story truth, a character's belief/knowledge and reader-visible revelation. Reader reveal state is not permission to leak protected material to a consumer.
- Define story-period references, boundary meanings and unknown/unbounded intervals. Creation timestamps and manuscript order are not a substitute for story-time validity.
- Use one primary owner for mixed-domain facts with explicit secondary references and reviewed transfer. Do not silently maintain two accepted copies.
- Source revision/anchor/currentness, accepted effect, accepting action/actor and owner receipt must remain inspectable. Source loss produces an honest missing/tombstone or review state, not guessed reconstruction.
- Keep provenance metadata governed by the existing provenance contract. Owners emit source/acceptance events; a proposed shared envelope does not authorize raw protected content retention.

This should settle the selected first classes and actions, not every future Character/Lore field or merge/split workflow. Advanced merge, transfer and historical inspection can remain unavailable if their exclusion is explicit and first-slice identity/lifecycle safety still works.

### Search and protection details

The inspected desktop manifests/lockfile and `app/main`/`app/shared` sources contain no SQLite/FTS import or dependency match. Foundation and Outline use JSON files; Ideas uses a versioned JSON document and atomic-file persistence. SQLite could still be selected for a rebuildable derived index, subject to a reviewed binding and packaged candidate.

The default FTS5 `unicode61` tokenizer folds case and removes Latin diacritics; phrase matching follows tokens. The sample `MATCH` query therefore does not define literal exact matching. Separate search semantics and owner anchor validation are required. Ordinary FTS tables also retain content copies, so derived status does not eliminate protected residue obligations. [SQLite FTS5 documentation](https://www.sqlite.org/fts5.html).

Permission must be consumer-specific. A source permitted in a local author view may still be excluded from AI context or outbound packaging. Conversely, AI exclusion should not automatically erase every allowed local author navigation path. Revalidate on query and source return, invalidate/rebuild affected projections on revocation, and define residue/cache cleanup. Later AI execution must recheck context eligibility before use; it cannot undo an already completed external disclosure.

Make the first search coverage a reviewed whitelist, for example current manuscript/structure, selected Outline/Ideas material and accepted card facts. Add Binder/asset metadata or qualified memory references only after their owner projections exist. Binder UI need not block an otherwise sound search slice over existing owners: make P8-C a dependency only for the source classes it actually supplies.
